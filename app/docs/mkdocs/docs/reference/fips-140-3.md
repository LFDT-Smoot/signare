# FIPS 140-3

This document states what Signare does and does not claim under FIPS 140-3, which steps of an Ethereum signature happen inside a validated cryptographic module, and what to check on each signing module before citing its validation.

The target audience of this document is system administrators, security reviewers and auditors assessing a Signare deployment.

## What Signare claims

Signare is an application, not a cryptographic module. It holds no CMVP (Cryptographic Module Validation Program) certificate and no CAVP (Cryptographic Algorithm Validation Program) certificate. Validation applies to the module that holds the keys, and Signare's role is to keep the private key inside such a module for its whole life. On the PKCS#11 and Azure Key Vault signing modules:

* The key is generated inside the module, or loaded with the module's own tooling (see [Supported Signing Modules](supported-modules.md)).
* Every signature is computed inside the module. Signare sends a 32-byte digest and receives the ECDSA signature.

The Local Key Vault is the exception: it is a software backend for development and is not a module at all (see [below](#local-key-vault-and-softhsm)).

Whether a deployment meets a FIPS 140-3 requirement therefore depends on the module behind Signare, on that module being configured in its approved mode of operation, and on which operations the module performs there. The rest of this page gives the facts an assessor needs.

## Where the module boundary falls

An Ethereum signature has three steps. Only the last one happens inside the module.

| Step | Where | Status under FIPS 140-3 |
|---|---|---|
| Encode the payload: the RLP transaction, the EIP-712 structure or the EIP-191 message | Signare | Not cryptography. |
| Hash it with Keccak-256 | Signare | Not an approved hash function. Keccak-256 as Ethereum uses it is not one of the FIPS 202 functions: it differs from SHA3-256 in its padding. |
| ECDSA over secp256k1 on the digest | module | secp256k1 is not an approved curve. It can be an *allowed* curve in the approved mode of operation, for blockchain-related applications only, under the conditions in the next section. |

Signare also derives the account address from the public key, again with Keccak-256, normalises the signature to the low-S form and determines the recovery identifier. None of that touches the private key.

## secp256k1 under FIPS 140-3

NIST SP 800-186 (February 2023), the curve companion to FIPS 186-5, lists secp256k1 in Appendix H.2 under *Other Allowed Elliptic Curves*: "The curve secp256k1 is allowed to be used for blockchain-related applications." It is not in the table of recommended curves.

Section C.A of the FIPS 140-3 Implementation Guidance, *Use of non-Approved Elliptic Curves*, sets the conditions under which a validated module may use it in the approved mode of operation:

* within ECDSA only, and "it shall not be considered approved unless CAVP testing is available";
* the module must also implement at least one CAVP-testable curve, so that the same ECDSA implementation carries a CAVP certificate;
* the module's Security Policy must state that the curve "may only be used in blockchain-related applications";
* the implementation "shall use approved underlying algorithms, such as the message digests".

A module that meets these conditions lists secp256k1 in its Security Policy among the non-approved algorithms or curves allowed in the approved mode of operation, with a reference to IG C.A, either as an ECDSA row in that table or in a separate curve table the row cites. That is the entry to look for. Two consequences follow for Signare:

* **The curve is covered; the hash is not.** The module receives a Keccak-256 digest that it cannot distinguish from any other 32 bytes. CAVP tests signing an externally computed digest as the *ECDSA signature generation component*, and the Implementation Guidance restricts that component to "the context of a FIPS 186-5 signature generation", which requires an approved hash function. An Ethereum signature is therefore not an approved security service, even on a validated module in its approved mode. The claim Signare supports is narrower: the private key is stored and used only inside a validated module operating in its approved mode, where ECDSA on secp256k1 is an allowed algorithm, and it was generated there unless it was loaded with the module's own tooling.
* **Only signing is needed.** The allowance is for ECDSA. Whether key agreement or key derivation on secp256k1 (ECDH, BIP-32, SLIP-0010) is permitted in approved mode differs between modules, and some block it. Signare needs only key pair generation and signing on secp256k1, so this does not affect it.

## What to check per signing module

### PKCS#11 hardware modules

Signare generates keys with `CKM_EC_KEY_PAIR_GEN` using the secp256k1 domain parameters (OID 1.3.132.0.10) and signs with `CKM_ECDSA` over a digest it has already computed. It asks for the private key with `CKA_SENSITIVE` true and `CKA_EXTRACTABLE` false, so the value can be neither read nor wrapped out, and reads both attributes back after generation: a token that reports otherwise has the key pair destroyed and the request fails. Before citing the module's validation:

1. **The certificate is Active and names the firmware you run.** Every FIPS 140-2 certificate has been on the CMVP Historical list since 22 September 2026. The CMVP validated modules page says that for a certificate marked historical, "Federal Agencies should not include these in new systems but can be procured for legacy systems", and the transition page that the CMVP "supports the purchase and use of these modules for existing systems". A new deployment that has to cite a validation needs an Active FIPS 140-3 certificate, and a certificate covers only the firmware versions it lists.
2. **The Security Policy lists secp256k1 ECDSA as allowed in the approved mode**, with the IG C.A reference, and the module is configured in its approved mode as the Security Policy describes.
3. **Key pair generation and signing on secp256k1 are permitted in that configuration.** Some vendors disable other secp256k1 operations in approved configuration. Signare does not use them.

Security Policies read in October 2026 that carry the IG C.A allowance for secp256k1: Marvell LS2 HSM Family, certificate 4703, Table 4, which is the module in AWS CloudHSM `hsm2m.medium`; Thales Luna G7, certificate 4962, Table 2-6, with sign and verify permitted and derive not; Thales Luna K7, certificate 4684, Table 2-3. All three cite IG C.A; none of them reproduces the blockchain-only statement the guidance asks the Security Policy to carry. The converse exists too: the Entrust nShield 5s policies for certificates 4745 and 4765 list only the NIST P curves, so secp256k1 is not available in that module's approved mode. Check the current certificate and Security Policy of the module you deploy rather than relying on this list.

### Azure Key Vault

Signare signs with the `ES256K` algorithm, so the key must be on curve `P-256K`. For the key to be held in an HSM it must be an `EC-HSM` key in Key Vault Premium or in Managed HSM; a software-protected `EC` key is not in an HSM on any tier.

Before the first signature with a key version, Signare reads the key, which needs the `keys/get` permission, and checks its type, curve and platform. By default a key that fails the check, or cannot be read, only produces a warning in the log, once per key version. With `hsmmodules.hardwareOnly` set it is refused (see [Hardening settings](#hardening-settings)). Each key records which platform holds it in its `hsmPlatform` attribute, as documented by Microsoft: `2` is the FIPS 140-3 Level 3 validated HSM platform, `1` the previous FIPS 140-2 Level 2 platform, whose certificates are now Historical, and `0` a software cryptographic module. New keys and key versions are created on the latest platform, and an existing key cannot be moved between platforms. A key on platform `1` is replaced by creating a new key version, which has a new public key and therefore a new account address.

### Local Key Vault and SoftHSM

Neither is a validated module. The Local Key Vault keeps keys in the database and signs in software; SoftHSM is a software PKCS#11 token used for testing. Both are for development only. With `hsmmodules.hardwareOnly` set, a Local Key Vault module cannot be created, no slot or key can be added to one, and an existing one refuses to sign; the `signare-nosofthsm` image does not carry SoftHSM at all.

## The Go toolchain

Signare is written in Go. Since Go 1.24 the approved algorithms in the standard library's cryptography are implemented by the Go Cryptographic Module, and module version v1.0.0 holds CMVP certificate 5247 (FIPS 140-3, overall Security Level 1). By default a Go build uses the module code in the toolchain's own source tree, not the validated version, and FIPS 140-3 mode is off. Signare does not change that default.

Building with `GOFIPS140=certified` links the validated module version and makes `GODEBUG=fips140=on` the binary's default. The alias names the latest module version that holds a CMVP certificate, so it follows later validations without a change here; the Go 1.27.1 toolchain this repository pins resolves it to v1.0.0. In that mode the module runs its integrity self-check and known-answer tests, `crypto/rand` is implemented as a NIST SP 800-90A DRBG, and, in the words of the Go documentation, "the `crypto/tls` package will ignore and not negotiate any protocol version, cipher suite, signature algorithm, or key exchange mechanism that is not FIPS 140-3 approved". The setting is read by `make -C deployment build` and is a build argument of the Docker image:

```console
GOFIPS140=certified make -C deployment build
docker build --build-arg GOFIPS140=certified -f app/Dockerfile -t signare:fips .
```

The resulting binary records the setting:

```console
$ go version -m signare | grep -E 'GOFIPS140|DefaultGODEBUG'
	build	DefaultGODEBUG=fips140=on
	build	GOFIPS140=v1.0.0-c2097c7c
```

What this covers in Signare is the standard library cryptography it links: the TLS connections to PostgreSQL and to Azure Key Vault, and the random numbers they draw from `crypto/rand`. It does not cover the Ethereum primitives. Keccak-256 comes from `golang.org/x/crypto/sha3` and secp256k1 from `btcec`, both outside the module and unchanged by the setting, so the position in the sections above is the same with or without it. The certificate lists the operating environments the module was tested on; whether your platform is among them is a question for the certificate, not for Signare. Go also offers `GODEBUG=fips140=only`, which makes non-approved algorithms return an error or panic; the Go documentation describes it as "a best effort mode meant for testing, assessment, and debugging" that "is not intended to be used in production".

## Hardening settings

Three settings keep a deployment inside the position above. None of them makes Signare a validated module.

* **`hsmmodules.hardwareOnly: true`** in the static configuration refuses the keys Signare could otherwise hold or accept in software: the Local Key Vault cannot be created, given slots or keys, or used to sign, and an Azure Key Vault key must be reported by the vault as `EC-HSM` on `P-256K` and, when the vault reports a platform, on platform `2`. A PKCS#11 library is trusted as configured. A refusal is `412 Precondition failed` on the REST API and `-32097 Precondition failed` on JSON-RPC; an Azure Key Vault refusal is also logged at warning level. Signare logs the policy at startup, together with whether the Go cryptographic module runs in FIPS 140-3 mode.
* **`--target signare-nosofthsm`** on the Docker build, or `DOCKER_TARGET=signare-nosofthsm` for `make -C deployment ci.docker_build`, produces an image without SoftHSM, for deployments that sign with a hardware HSM or Azure Key Vault. The default `signare` image keeps SoftHSM for development and testing.
* **`GOFIPS140=certified`** on the build, as described in [The Go toolchain](#the-go-toolchain). `make -C app fips_test` runs the application test suite built that way.

## Beyond FIPS 140-3

NIST IR 8547, *Transition to Post-Quantum Cryptography Standards*, still an initial public draft dated November 2024, proposes that ECDSA at 112 bits of security is deprecated after 2030 and that ECDSA at every security strength is disallowed after 2035 for federal use. That would cover secp256k1 and P-256 alike. It is a draft, and it is the transition that affects the curve rather than the certificate.
